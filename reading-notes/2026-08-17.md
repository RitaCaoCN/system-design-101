## 问题 1：对象存储相对于文件存储和块存储，在技术路线上有什么特殊的地方吗？

**参考答案：** 有。对象存储的特殊之处不只是“也能存文件”，而是换了一套数据模型和访问方式：放弃磁盘/目录那种就地改字节的能力，换规模、成本和把元数据跟数据绑在一起。

用例文的对比是：文件存储用层级目录，块存储把文件切成等大小 block，对象存储把 metadata 和对象本身一起保存，格式更灵活、更容易扩展。同一系列的 [存储系统概览](/Users/rita/study/system-design-101/translations/zh/storage-systems-overview.zh.md) 把取舍说得更直白：牺牲性能，换高持久性、超大规模和低成本，主要面向相对“冷”的数据。

三种存储是三层抽象：

```text
对象存储   一个 object = 数据 + 自定义 metadata
           用 bucket + key 找，HTTP PUT/GET
                ↑ 不再假装自己是一块盘或一个文件夹

文件存储   目录树 + 文件名（NFS / SMB）
           建立在块存储之上
                ↑

块存储     等大小的 block，按偏移读写
           对服务器来说就是一块裸盘（本机盘 / iSCSI / EBS）
```

- 块存储：给操作系统一块“生肉盘”。数据库、虚拟机喜欢它，因为可以按 block 随机读写，延迟低。归单台服务器所有，不是共享资源。
- 文件存储：在块上面加目录和文件，用路径访问，适合多人共享文件夹。
- 对象存储：不再提供盘或目录，而是提供 HTTP 上的对象仓库（S3、GCS、Azure Blob）。

技术路线上真正特殊的几点：

1. **扁平命名，而不是目录树。** 文件存储的路径是 `/photos/2026/08/a.jpg`，目录一深、文件一多，元数据服务很难水平拆。对象存储一般是 `bucket + key`，key 只是字符串（看起来像路径，其实只是名字）。定位对象常常对 key 做哈希、落到某台机器，所以横向加机器就能扩容。用例文说的“更容易扩展”、云原生存储、数据湖，都靠这条。
2. **元数据和数据绑在一起。** 块存储几乎不认“这是一张图”；文件存储只有 inode 那类固定属性。对象存储把自定义 metadata 和对象一起存，例如 `content-type=video/mp4`。下游可以按对象做生命周期、权限、检索，而不必再维护一套外部索引。
3. **整对象写入，通常不能改中间几个字节。** 块存储可以改第 3 个 block；文件存储可以 seek 后改文件中间。对象存储典型接口是整份 PUT 上去，要改就整份覆盖（大文件用 multipart 分片传，最后在服务端拼成一个对象）。所以适合一次写、多次读：备份、归档、视频、数据湖文件；不适合当数据库盘或虚拟机系统盘。
4. **接口是 REST API，不是挂载盘。** 块是 SCSI/iSCSI，文件是 NFS/SMB，对象是 `PUT / GET / DELETE`。云原生应用不用先挂盘、格式化，拿 SDK 就能存。代价是延迟明显高于块和文件，更偏“冷”数据。
5. **为规模和持久性而设计的内部实现。** 对象存储集群通常把对象打散到很多机器，用复制或纠删码换持久性，而不是一块 RAID 卡管一柜子盘。单对象可以很大、总容量可以到 EB 级，单 GB 成本低，所以归档、备份、数据湖、IoT 原始数据会选它。

对照：

| | 块存储 | 文件存储 | 对象存储 |
|---|---|---|---|
| 访问单位 | 固定大小的 block | 文件 + 目录 | 整个 object |
| 怎么找数据 | 块号 / 偏移 | 路径 | bucket + key |
| 典型接口 | 本地盘、iSCSI、云盘 | NFS、SMB | HTTP REST |
| 部分修改 | 可以 | 可以 | 基本整份覆盖 |
| 元数据 | 几乎没有 | 固定 inode | 自定义，和对象一起存 |
| 谁在用 | 一台服务器独占 | 多机共享目录 | 多服务通过 API 共享 |
| 优化目标 | 低延迟、随机 IO | 好用、共享 | 规模、耐久、便宜 |

对象存储不是“更好的网盘”，而是：不做 POSIX 文件系统，做成可无限堆对象的分布式仓库。Netflix 片源、数据湖里的 Parquet、数据库备份适合它；MySQL 数据目录、虚拟机磁盘仍然用块存储，团队共享工作盘仍然用文件存储。
