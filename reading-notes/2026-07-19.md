## 问题 1：MySQL 用的难道不是 B+ 树吗？B+ 树比 B 树是不是还多了双向链表？

**参考答案：** 对，MySQL InnoDB 里常说的 “B-Tree 索引” 严格讲实现的是 B+ 树，不是经典意义上的 B 树。B+ 树的特点是非叶子节点只做导航，真正的数据都在叶子节点；叶子节点之间通常还会用链表连接，数据库实现里常见的是双向链表，方便范围查询和顺序扫描。

## 问题 2：B 树和 B+ 树的区别是什么？

**参考答案：** B 树的数据可以存放在所有节点中，查到中间节点时可能就已经命中数据；B+ 树只有叶子节点存数据，非叶子节点只存 key 和子指针。B+ 树的叶子节点按顺序连接起来，因此更适合范围查询、排序和顺序扫描。数据库更常用 B+ 树，是因为它在磁盘页利用率、树高和范围访问上更适合数据库场景。

# [B-Tree vs. LSM-Tree](/Users/rita/study/system-design-101/data/guides/b-tree-vs.md)

阅读时间：2026-07-19

## 问题 1：LSM 有什么用？

**参考答案：** LSM 树的主要用途，是把“昂贵的随机写”转化成“便宜的顺序写”，从而显著提升写入吞吐。传统 B+ 树在更新数据时，经常需要修改磁盘页、分裂节点、维护平衡，这些操作会带来较多随机 I/O；而 LSM 树会先把写入放到内存里的 memtable，再批量刷盘生成有序的 SSTable，最后通过后台 compaction 把多个文件合并整理。这样做的好处是写入路径非常短，适合高并发写、多批次写、日志型数据和 KV 存储场景。

LSM 的代价也很明确：读取时可能要检查多个层级和多个 SSTable，因此读放大通常更高；后台 compaction 会反复搬运数据，因此会引入写放大；同时实现上也更复杂，需要处理 compaction 策略、Bloom filter、层级管理和故障恢复等问题。也就是说，LSM 不是“整体更快”，而是把性能重心明显偏向写入吞吐。

## 问题 2：RocksDB 为什么更像写入引擎，InnoDB 为什么更像事务数据库引擎？

**参考答案：** RocksDB 的设计核心是 LSM，所以它更像一个“高吞吐写入引擎”。它擅长把写请求快速接住，先进入内存，再顺序落盘，之后由后台线程慢慢整理。这个模型非常适合大量写入、日志追加、嵌入式存储和 KV 场景，因为它追求的是写性能、存储压缩能力和工程可扩展性，而不是复杂的 SQL 事务语义。

InnoDB 则是典型的事务数据库存储引擎，它的目标不是单纯追求写入吞吐，而是同时满足事务、一致性、并发控制和范围查询等需求。InnoDB 使用 B+ 树组织索引，支持 MVCC、行锁、崩溃恢复和 SQL 事务语义，因此它更强调“正确地读写”和“稳定地支持事务”，而不是单方面把写入做到极致。换句话说，RocksDB 更像“把数据尽快写进去再慢慢整理”，InnoDB 更像“把数据组织成适合事务和查询的形态”。

从使用场景上看，RocksDB 更适合写多读少、以 key-value 访问为主、并且能接受后台合并成本的场景；InnoDB 更适合 OLTP、事务处理、范围查询和需要强一致性的关系型数据库场景。两者都能管理数据版本，但它们优化的目标完全不同：RocksDB 优先写入吞吐，InnoDB 优先事务能力和查询平衡。

# [OLTP / OLAP](/Users/rita/study/system-design-101/translations/zh/how-do-you-decide-which-type-of-database-to-use.zh.md)

阅读时间：2026-07-19

## 问题 1：OLTP 和 OLAP 是什么？

**参考答案：** `OLTP` 是 `Online Transaction Processing`，中文通常叫在线事务处理，主要用于下单、支付、登录、转账、修改资料这类高频小事务场景，特点是读写频繁、强调事务一致性和并发控制。`OLAP` 是 `Online Analytical Processing`，中文通常叫在线分析处理，主要用于报表、统计、指标看板、日志分析这类聚合查询场景，特点是经常扫描大量数据、做分组汇总，更重视分析查询性能。

## 问题 2：MySQL 和 ClickHouse 分别更适合什么场景？

**参考答案：** MySQL 更常用于 `OLTP`，也就是在线业务库，负责处理核心业务写入和事务操作。ClickHouse 更常用于 `OLAP`，也就是分析型数据库，负责报表、日志分析、指标统计和大规模聚合查询。更准确地说，ClickHouse 不是单纯“离线分析用”，它也可以做准实时分析，只是它的设计重点明显偏向分析查询而不是事务处理。

# [数据库类型简介](/Users/rita/study/system-design-101/translations/zh/how-do-you-decide-which-type-of-database-to-use.zh.md)

阅读时间：2026-07-19

## 问题 1：Oracle、MySQL、MariaDB、SQLite、PostgreSQL、Redis、ClickHouse、MongoDB、S3、Ceph 分别是什么，它们各自适合什么场景？

**参考答案：** 这几个系统可以按用途分成几类来看。

`Oracle` 是企业级关系型数据库，功能非常完整，常用于金融、政企、核心交易系统这类对稳定性、可用性、权限、审计和复杂 SQL 都要求很高的场景。它的优势是成熟、强大、可控性高；代价通常是成本和运维复杂度更高。

`MySQL` 是最常见的通用关系型数据库之一，生态广、资料多、上手快，适合绝大多数 Web 业务和中小型到大型的在线业务系统。它通常被当作业务主库来使用，特别适合事务型读写。

`MariaDB` 是从 MySQL 演化出来的开源分支，语法和使用方式与 MySQL 很接近，适合想保留 MySQL 兼容性、同时继续使用开源路线的团队。很多场景下，它可以看作 MySQL 的替代选择之一。

`SQLite` 是嵌入式关系型数据库，不需要单独起服务，整个数据库就是一个本地文件。它非常适合移动端、桌面应用、单机工具、测试环境和轻量级本地存储，但不适合高并发、多写入的服务端业务。

`PostgreSQL` 也是关系型数据库，但通常被认为能力更全面，尤其擅长复杂查询、扩展能力、事务、JSON、地理信息和标准 SQL 支持。它很适合对数据一致性、查询能力和可扩展性要求都比较高的系统。

`Redis` 是以内存为主的键值存储，速度非常快，常用于缓存、会话、排行榜、计数器、限流、分布式锁和简单消息场景。它的核心价值是低延迟和高吞吐，但一般不作为核心业务主库来替代关系型数据库。

`ClickHouse` 是分析型列式数据库，特别擅长大规模聚合、统计报表、日志分析和指标查询。它通常用于 OLAP 场景，适合“读很多数据、做很多汇总”的任务，不太适合高频事务写入。

`MongoDB` 是文档型数据库，数据以文档形式组织，字段结构灵活，适合业务模型变化快、字段不固定、迭代频繁的场景，比如内容管理、产品目录、事件数据和部分半结构化数据存储。

`S3` 是对象存储服务，更像“存大文件的仓库”，适合图片、视频、备份、日志、数据湖文件和静态资源。它不是传统数据库，而是面向非结构化对象存储的基础设施。

`Ceph` 是开源分布式存储系统，可以提供对象存储、块存储和文件存储能力。它常用于私有云、自建存储集群、备份和大规模存储底座，也不是传统意义上的数据库。

## 问题 2：这些系统怎么快速选型？

**参考答案：** 如果是核心业务、事务一致性强的在线系统，通常优先选 `MySQL` 或 `PostgreSQL`；如果是企业级复杂场景和商业支持需求较强，可以考虑 `Oracle`；如果是轻量本地存储，可以选 `SQLite`；如果需要高速缓存、计数、排行榜或锁，适合用 `Redis`；如果是海量统计、报表和日志分析，适合用 `ClickHouse`；如果数据结构变化大、字段不固定，适合用 `MongoDB`；如果要存图片、视频、备份等大对象，更适合用 `S3` 或 `Ceph`。

## 问题 2：向量数据库一般适合什么场景？

**参考答案：** 向量数据库主要用于相似度检索和语义搜索，常见场景包括 RAG、推荐系统、图片搜索、文本相似度匹配和 embedding 检索。它的核心能力不是传统 SQL 事务，而是高效存储向量并支持近邻搜索，所以更适合 AI 检索和语义理解相关场景。实际使用中，它通常会和现有数据库配合，而不是完全替代关系型数据库或文档数据库。

# [6 种数据库模型](/Users/rita/study/system-design-101/data/guides/top-6-database-models.md)

阅读时间：2026-07-19

## 问题 1：关系模型和星型数据库有什么区别？

**参考答案：** 关系模型是通用数据组织方式：用表、行、列表达数据，通过主键/外键和规范化保证完整性、减少冗余，查询语言是 SQL，适合传统业务库和复杂关系查询。星型模式（Star Schema）是面向数据仓库 / OLAP 的专用表结构：中心是存度量数据的事实表，周围是描述属性的维度表，目标是让分析查询更简单、Join 更少、取数更快。星型通常仍建在关系库之上，是分析场景下的表布局，而不是另一种独立数据库引擎。一句话：关系模型管“数据怎么存、怎么保证正确”；星型模式管“分析报表怎么查得又快又简单”。

## 问题 2：Network Model 是一种图数据库吗？

**参考答案：** 不完全是。网络模型（Network Model）和现代图数据库在思想上接近——都能表达多对多、图状结构——但不是同一种东西。网络模型是 1960–70 年代的经典数据模型（如 CODASYL/IDMS），结构预定义、偏指针导航；现代图数据库（如 Neo4j）以节点、边为一等公民，常用 Cypher 等声明式查询。指南说网络模型形成 graph structure，是指数据结构上像图（一条记录可有多个父、多个子），用来弥补层次模型只能单父的限制。

## 问题 3：为什么文档里 Network Model 用 Neo4j 举例？

**参考答案：** 正文文字并没有写 Neo4j，是示意图在 Network Model 栏下贴了 Neo4j logo。这是 ByteByteGo 的教学简化：突出“节点可有多个父、形成多对多图结构”这一特征和 Neo4j 很像，所以用它当现代对照物。严格区分时，Network Model 是 CODASYL 时代的经典模型，Neo4j 是现代图数据库产品；图上是“长得像”的对照，不是 Network Model ≡ Neo4j。

## 问题 4：Neo4j 是什么？

**参考答案：** Neo4j 是常见的原生图数据库：数据以节点（Node）和关系（Relationship）组织，两者都可带属性；节点可用标签分类（如 `:User`）；查询语言常用 Cypher（声明式模式匹配）。适合社交关系、推荐、知识图谱、风控路径排查、权限/网络拓扑等多跳关联场景；一般不替代普通业务主库做重度事务或报表聚合。

## 问题 5：有什么产品用了 Neo4j？

**参考答案：** 很多大公司是在某个功能模块里使用，不是整站替换。公开案例包括：eBay（推荐/个性化）、WestJet（机票预订推荐）、Comcast/Xfinity（智能家居身份与权限关联）、Enel（电网数字孪生）、BT Group（网络资产关系）、Intuit（客户数据相关图分析）、BNP Paribas Personal Finance（反欺诈）、Gilead Sciences（医药欺诈/关系分析）。常见落点是推荐、风控、知识图谱、权限、供应链/网络拓扑、数字孪生。

# [什么是 Serverless DB？](/Users/rita/study/system-design-101/translations/zh/what-is-serverless-db.zh.md)

阅读时间：2026-07-19

## 问题 1：Serverless DB 是如何实现自动扩缩容的？

**参考答案：** 以 Aurora Serverless 为例，核心是把计算层和数据存储层解耦：负载变化时主要增减计算资源，共享存储仍在，不必整实例搬数据。平台按业务负载自动启停与扩缩，应用无需像传统云库那样人工创建和管理实例；还可把 provisioned 实例并进 serverless 池，混合使用。文章侧重架构思路，未展开具体调度算法细节。

## 问题 2：自动扩缩容是根据并发量吗？

**参考答案：** 不完全是只看并发。实现上通常按 Aurora Capacity Unit（ACU）背后的整机负载调度，常见信号包括 CPU、连接数、内存等。并发/连接会推高负载，但一条很重的 SQL 即使并发不高也可能触发扩容；空闲时则缩容甚至（部分版本）冷却后关掉计算。一句话：监控负载 → 调节计算容量，并发只是负载的一部分。

## 问题 3：大量请求是先堆积在代理层，扩容后再打到新的业务 endpoint 吗？

**参考答案：** 不是。代理层主要做连接保持与路由，不是业务请求积压队列；请求通常立刻打到当前已有计算节点，算力不够时表现为变慢、排队或超时/拒绝，同时平台在背后加 ACU。扩容后客户端一般仍连同一个集群 endpoint，容量变化发生在 endpoint 后面的计算层，业务不必改连新地址。路径大致是：App → 固定 endpoint → Proxy/Router → 可扩缩的 Compute → 共享 Storage。

# [如何选择正确的数据库](/Users/rita/study/system-design-101/translations/zh/how-to-choose-the-right-database.zh.md)

## 问题 1：配图里的 HDFS 是用来处理 video 和 image 的吗？之前一直用来做数据分析

**参考答案：** 不是。配图把 HDFS 和 video/image 放一起，意思是「大文件、非结构化 blob 适合用分布式文件系统或对象存储来存」，不是说 HDFS 专门用来处理音视频。

HDFS 本质是存储层，适合存大文件、一次写多次读；视频、图片只是例子，日志、Parquet、备份同样适用。用 HDFS 做数据湖、再配合 MapReduce/Spark/Hive 做分析，才是更典型的用法，和「把媒体文件落盘」并不矛盾，只是负载不同。

配图真正想对比的是：这类大文件不要整段塞进 OLTP 数据库；应外置到 HDFS/S3，元数据再放库里。今天存媒体更常见的是对象存储（S3/GCS/Blob），HDFS 更常见于自建大数据分析集群。

# [20 行解释时序数据库 TSDB](/Users/rita/study/system-design-101/translations/zh/time-series-db-tsdb-in-20-lines.zh.md)

阅读时间：2026-07-19

## 问题 1：TSDB 的功能看起来可以用 MySQL 实现，为什么还需要 TSDB？

**参考答案：** 小规模时 MySQL 完全能当「简陋 TSDB」用（一张带时间戳和标签的表就能存能查）。单独要 TSDB，是因为时序负载的量级和访问模式会把通用 OLTP 库打得很疼。

文章也说了：表面像关系表，底层却按 `[Measurement, Tag, Field]` 拆进 TSM，为「按时间 + 标签做聚合」优化。和 MySQL 的主要差别在于：

1. **写入**：指标/传感器是持续追加、几乎不改旧值；TSDB 走 append / 类 LSM 路径，MySQL（InnoDB）更擅长事务更新，海量追加时写放大和索引维护成本高。
2. **查询**：几乎总是时间窗口 + 标签筛选 + 聚合；TSDB 的数据布局为此而生，MySQL 靠索引硬扛，序列一多、窗口一长就容易慢。
3. **压缩与留存**：时序压缩比极高，再加自动过期、降采样；MySQL 行存占空间大，过期/rollup 多半自己造轮子。
4. **成本**：监控高 QPS、留几个月原始点时，磁盘和 CPU 通常远高于专用方案。

粗算对照（1 万机 × 100 指标 × 15s）：约 6.7 万点/秒、每天约 58 亿点；30 天原始点 MySQL 行存+索引常到十几 TB 量级，TSDB 压缩后常到几百 GB 量级。功能可重叠，优化目标不同——MySQL 保证语义正确，TSDB 保证时序负载下可持续的成本与延迟。

## 问题 2：MySQL 扫行页 + GROUP BY、TSDB 按序列定位 + 块内聚合，是因为表设计不一样吗？是不是 MySQL 一张表、TSDB 磁盘上已经有多张表？

**参考答案：** 不完全是。差别主要不在「SQL 表有几张」，而在**物理怎么排布**，以及有没有另做时间轴上的预处理。

**1. 用户视角可以都是「一张表」**  
文章也写了表面和关系表差不多。你仍然可以把它理解成一个 `weather` / `cpu` measurement。并不是业务上必须建很多 SQL 表，TSDB 才快。

**2. 真正不同的是物理布局**  
- MySQL（InnoDB）：逻辑上一张（或按月分几张）表，行是 `[ts, host, metric, value]`；磁盘上主要是 B+ 树页，按主键/索引键排序。即便主键是 `(host, metric, ts)`，查「过去 24h 按 region 聚合」时，仍常要扫大量叶子页，再在执行层做 `GROUP BY`。行展开存、压缩弱，同样一段时间往往要读更多字节。  
- TSDB（文中的 TSM）：逻辑上还是一个 measurement；落盘时按 `[Measurement, Tagset, Field]` 拆成很多**时间序列（series）**，每个 series 内部按时间追加成块。文中说 weather 进 4 个 TSM，指的是这类按 measurement/tag/field 切开的时间块，**不是**业务库里的多张业务表。查某 tag 组合时：先用 tag 索引定位相关 series，再只读这些 series 在时间范围内的块，聚合尽量在块上做。

对照直觉——「`host=web-01` 过去 1 小时的 `cpu`」：MySQL 在大表里用索引找范围，读出很多完整行再聚合；TSDB 的 `cpu` + `host=web-01` 几乎就是一条序列，只读这一条在 1 小时内的时间块（往往已压缩）再汇总。

**3. 「1m 预聚合」是另一层优化**  
指后台物化好的降采样结果（连续查询 / rollup），例如原始 15s 留一套，再写出「每分钟一个点」的摘要。这有点像 MySQL 自己维护 `metrics_1m`，但 TSDB 常内置。它和「TSM 按序列切开」是两层：布局让原始点范围扫更省；预聚合让看板若只要 1m 粒度，甚至不用碰原始点。

**一句话：** 不是「表多就快」，而是 TSDB 写盘时已经按时间序列和时间块组织好了；MySQL 一张大表里行通存，主要靠 B+ 树定位，时序范围聚合不是主场。预聚合则是在这之上再存一层粗粒度结果。
