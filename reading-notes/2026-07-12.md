## 问题 1：Materialized View 具体是什么意思？它和 cache 有什么区别？

**参考答案：** Materialized View 可以理解为“预先算好并持久化保存的查询结果”。它和普通 View 不同，普通 View 只保存查询定义，不存数据；Materialized View 会把查询结果真正写到磁盘上，因此查询时可以直接读取已有结果，速度通常会更快。

例如，假设有一张订单表 `orders(id, user_id, amount, created_at)`，而业务经常要查“每个用户每天的订单总额”：

```sql
SELECT user_id, DATE(created_at) AS day, SUM(amount) AS total_amount
FROM orders
GROUP BY user_id, DATE(created_at);
```

如果订单很多，这个聚合每次都现算会比较慢。可以建一个 `Materialized View`，提前把结果算好并保存起来：

```sql
CREATE MATERIALIZED VIEW daily_user_sales AS
SELECT user_id, DATE(created_at) AS day, SUM(amount) AS total_amount
FROM orders
GROUP BY user_id, DATE(created_at);
```

之后查询时直接读这个视图：

```sql
SELECT total_amount
FROM daily_user_sales
WHERE user_id = 123 AND day = '2026-07-12';
```

这样通常会比每次扫描原始订单表再聚合快很多。

它和 cache 相似，都是为了加速读取，也都可能面对数据不是最新的问题，但两者不同在于：cache 通常是应用层或中间层的临时热数据副本，Materialized View 是数据库层的正式对象，只适合缓存查询结果，并由数据库负责刷新或更新。

## 问题 2：CQRS 和 Index Table 看起来很像，它们是什么关系？

**参考答案：** 它们确实有相似点，因为都体现了“主数据结构负责写，另一个结构负责更快地读”的思路。但两者不是同一个层次的概念。

比如在电商系统里，主表可能是：

```sql
orders
- order_id
- user_id
- status
- created_at
```

如果业务经常要“按用户查订单”，可以再建一张索引表：

```sql
orders_by_user
- user_id
- order_id
- created_at
- status
```

这样查询某个用户的订单时，直接扫 `orders_by_user` 会比扫主表更快。这就是 `Index Table`，它更像是一个为某类查询专门设计的辅助表，目标很具体，结构也通常比较简单。

`CQRS` 则是更大的架构模式。还是上面的电商系统，写入侧负责下单、支付、取消；读取侧负责订单列表、订单详情、统计页面。读侧可能不止一张表，甚至可以是多张专门用于展示的数据结构，比如：

```text
- 订单列表表
- 订单详情表
- 用户订单索引表
- 统计报表表
```

所以更准确地说，`Index Table` 可以看作 `CQRS` 里读模型的一种实现方式，而不是 `CQRS` 本身。
