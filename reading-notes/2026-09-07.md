阅读时间：2026-09-07

## 问题 1：文档说 Redis Cluster 不支持 separating write and read，但 Redis 不是支持读写分离吗？

**参考答案：** 不矛盾。文档说的是 **Redis Cluster**，不是泛指所有 Redis。爱奇艺分享里其实分得很清：

| | Master–Slave（+ Sentinel） | Redis Cluster |
|---|---|---|
| 读写分离 | **常用** | **基本不当标配** |
| 爱奇艺做法 | Master 绑读写域名，多个从库绑读域名 | 读写主要打各 slot 的 **主节点** |

所以：「Redis 支持读写分离」通常指 **主从复制** 那套（写主、读从）；「Cluster 不支持 separating write and read」指 **Cluster 默认/主流用法里读也走主**，不是主从那套读写分离模型。原文大意也是：Cluster 功能受限……读写只在主库上。

原因简要：

1. Cluster 模型重心是 **分片**，不是读扩展；要扛更多读，更常见是加更多主分片。
2. 默认路由按 key 找 slot，再打到该 slot 的 **master**；写和读默认都去主。
3. 从库读不是一等公民（尤其早期）；后来虽有 `READONLY`，但要客户端显式支持，还要接受复制延迟。
4. 和主从的运维心智不同：主从一个主+多个从，好拆读写；Cluster 很多主+各自主的从，从库读要按 slot 找对 replica，复杂度高。

一句话：Redis 能读写分离（主从场景很常见）；选型树说的是 Redis Cluster 默认不把「写主读从」当核心能力。

## 问题 2：最新的 Redis 也是默认读主吗？是不是 Cluster 模式才读写分离？

**参考答案：** 结论和常见直觉**正好相反**。最新开源 Redis Cluster **默认仍是读主**。

官方 Cluster 规范至今仍是：replica **默认会把请求重定向到对应 slot 的 master**；想读从库，客户端必须先发 `READONLY`（声明愿意读可能旧的数据）。因此：

- **默认：读 + 写都打 master**
- **读从：可选能力**，要客户端显式开启（如 `read_from_replicas=True` / Lettuce `ReadFrom.REPLICA`），不是 Cluster 开箱自带的读写分离
- 很多客户端默认也不开；replica 主要还是给 failover 备份用

两种模式怎么记：

| | Master–Slave | Redis Cluster |
|---|---|---|
| 默认读哪里 | 你连谁读谁；业务常自己做成「写主读从」 | **默认读主**（和写一样） |
| 读写分离 | **很常见、很好做**（读域名/读从） | **不是默认**；要额外开 `READONLY` |
| 扩读常见手段 | 加从库 | 更常靠 **加更多 master 分片**；读从是可选优化 |

容易混反的点：不是「Master–Slave 默认读主、Cluster 才读写分离」，而是：**Master–Slave 很容易配成读写分离；Cluster 默认不分离，读写分离要自己开**。爱奇艺那句「Cluster 读写只在主库」，和现在最新开源 Redis 的默认行为仍然一致。

## 问题 1：SSTable 是什么？

**参考答案：** SSTable = **Sorted String Table**（有序字符串表）。文档写法是「不可变的磁盘版 Map」。

可以想成磁盘上「排好序、写完就锁死」的 key→value 文件：

1. **磁盘上的 Map**：按 key 存 value，落在文件里，不是内存 HashMap。
2. **Sorted**：文件内 key 有序，方便二分查找，也方便和别的 SSTable 归并。
3. **Immutable**：写完不能改。要更新就写新文件；旧数据靠之后的 compaction（合并）清理。

为啥「不能改」反而有用：磁盘原地改一行又慢又麻烦。SSTable 做法是——写入先堆在内存（如跳表），满了再**顺序刷**成一个新 SSTable；更新/删除不当场改旧文件，而是写新版本；过一阵合并多个文件丢掉过期数据。磁盘最喜欢顺序写，所以写很快。

读 `key` 时：先查内存最新值，再查最近刷盘的 SSTable，再往更老的文件找。每个文件内可二分，但可能要查多个文件——这是用读换写的代价。

文档里 **LSM tree ≈ Skiplist（内存）+ SSTable（磁盘）**，偏高写入吞吐。和 B-tree 对比：B-tree 原地更新、读写较均衡；SSTable + LSM 偏写优化。Cassandra、LevelDB、RocksDB、Bigtable 都大量用这个模型。

一句话：**SSTable = 磁盘上「排好序、写死不能改」的 key→value 文件；靠不断写新文件 + 定期合并，支撑高写入数据库。**
