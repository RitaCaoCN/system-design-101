## 问题 1：Couchbase 和 Redis 有什么区别？

**参考答案：** 两者都能很快，但解决的问题不同，不是「两个差不多选一个」。

| | Redis | Couchbase |
|---|---|---|
| 本质 | 内存型键值存储（也可当高速库） | 分布式多模型文档型 NoSQL |
| 数据形态 | string / list / set / zset / hash 等 | JSON 文档为主，也支持按 key 的 KV 访问 |
| 持久化 | 可选（RDB/AOF），默认以内存为主 | 磁盘持久化是常态，热数据常驻内存 |
| 典型用途 | 缓存、会话、计数、排行榜、限流、Pub/Sub | 业务文档主存、高并发读写、可查询的 NoSQL |
| 查询能力 | 主要按 key / 数据结构命令访问 | 按 document id 极速取文档，也能查询、建索引 |

直观比喻：

- **Redis ≈ 收银台旁的小冰箱**：东西全在「记忆」里，拿得极快；适合热门榜、登录 session、限流计数、「这个视频刚看过」这类临时/热数据。断电或重启后可能要重新装货（虽能持久化，但大家主要拿它当快取）。一般用 key 直接拿，例如 `user:123:session`。
- **Couchbase ≈ 带高速取货口的大仓库**：真正的货在仓库里（磁盘），常用的放在门口架子上（内存）。适合存整份 JSON 业务文档（播放记录、收藏列表、视频元数据等），目标是「这就是你的数据库」，不是临时加速层。

放到爱奇艺场景：用户刚点开的视频标题、封面 URL —— 几秒内反复读、丢了也能再查库 → 更像 Redis；用户播放记录、收藏、要长期存还能查的业务文档 → 更像 Couchbase。文中把 Couchbase 写成「分布式多模型 NoSQL 文档型数据库」，Redis 通常落在缓存 / 高速 KV 一侧。

## 问题 2：Couchbase 的优势是什么？是文件存储吗？MongoDB 不是也可以吗？

**参考答案：** Couchbase **不是文件存储**（那种存视频、图片的对象存储 / OSS）。它存的是 **JSON 文档**（一份份结构化业务数据），和 MongoDB 同一大类：文档型 NoSQL。

相对「纯磁盘文档库」或「纯缓存」，Couchbase 更像：**文档数据库 + 自带内存层（很像内置了 Memcached）**。常见卖点：

1. **读写可以很快**：热数据常在内存，按 document id / key 访问延迟低，适合高并发读。
2. **又能当持久化主库**：数据落盘，不是「缓存丢了就算了」。
3. **一条链路里既有 KV，又能查**：简单用 id 取整份文档很快；需要时还能用类似 SQL 的 N1QL、索引、全文检索等。
4. **天生偏分布式**：分片、副本是产品设计的一部分，爱奇艺这类规模会看重。

所以优势不是「能存文件」，而是：**文档要持久存，同时还要尽量像缓存一样快**。

那 MongoDB 不是也可以吗？**可以。** 很多场景 MongoDB 完全能扛文档存储。两者重叠很大，差别更像产品取向：

| | Couchbase | MongoDB |
|---|---|---|
| 核心印象 | 文档库，内存缓存味道很重 | 文档库，查询/生态更强、更通用 |
| 访问习惯 | 常强调先按 key/ID 极速读写 | 常强调灵活查询、聚合、丰富驱动 |
| 缓存角色 | 自己就常被当「库 + 缓存」 | 生产上更常见「Mongo + Redis」 |
| 选型现实 | 团队历史、运维经验、性能模型、成本 | 同上 |

爱奇艺同时列了 Couchbase 和 MongoDB，说明不是「二选一哲学正确」，而是有的业务选 Couchbase（更看重内存加速 + 分布式 KV/文档），有的选 MongoDB（更看重文档模型与查询/生态），Redis 继续专门做缓存、会话、计数。

## 问题 3：Couchbase 唯一的亮点是 JSON 可以索引吗？

**参考答案：** **不是。**「JSON 能建索引」完全不是 Couchbase 的独特亮点——MongoDB、甚至不少关系库的 JSON 字段也能建索引。这是文档库的标配，不是独门绝技。

Couchbase 真正常被拿来说的，是这几件事叠在一起：

1. **内存优先的访问路径**：热数据常在内存里，按 document id 读写可以非常快，更像「库自带缓存层」。
2. **一套系统里同时能当 KV 和文档库**：简单场景 `get(docId)` 极速取整份文档；复杂场景再上查询、索引。不必强制拆成「Redis 管快 + Mongo 管存」（当然很多人还是会拆）。
3. **分布式是默认形态**：分片、副本、跨节点扩展是产品中心能力。
4. **多服务/多模型能力**：除了文档，还有查询、全文检索、部分分析等（具体看版本与部署），所以文里写「多模型」。

判断口诀：如果只需要「存 JSON 还能按字段查」→ MongoDB 通常就够；会专门上 Couchbase → 多半冲着 **高并发下的内存型读写体验**，而不是冲着「居然能索引 JSON」。

## 问题 4：MongoDB + Redis 就可以覆盖 Couchbase 的能力了吗？

**参考答案：** **大体可以，很多团队就是这么干的。**

`MongoDB（持久化文档） + Redis（内存加速）` 在能力面上，能覆盖 Couchbase 最常见的那一块：

- 文档存得住、能查、能索引 → MongoDB
- 热数据要极快 → Redis

爱奇艺自己也同时列了这三样，说明现实里本来就不是「有 Couchbase 就不用另外两个」。

但不是 1:1 等价：

| | Couchbase | MongoDB + Redis |
|---|---|---|
| 系统数量 | 通常 1 套 | 2 套 |
| 一致性 | 同一份数据模型里处理 | 要自己处理缓存同步 / 失效 / 双写 |
| 运维 | 一套集群、一套监控 | 两套容量、故障、版本、备份 |
| 开发心智 | 多数时候打一个系统 | 要想「这段读 Redis 还是 Mongo」 |

所以差距往往不在「能不能做」，而在：

1. **缓存一致性谁来保证**（最麻烦）
2. **运维和故障面变大**
3. **延迟路径是否稳定**（Couchbase 热数据本就在内存；Mongo + Redis 要设计好才稳）

什么时候 Mongo + Redis「就够了」：业务已有 Mongo / Redis 经验；能接受自己做 cache aside、失效、穿透保护；不需要 Couchbase 那套一体化运维/授权模型。大多数互联网业务，这条路完全成立。

什么时候还会看 Couchbase：想少维护一套中间件，文档库自己就够快；访问模式非常偏「按 ID 海量读写」；团队历史栈就是 Couchbase。

一句话：能力上，`MongoDB + Redis` 通常能覆盖 Couchbase 的主战场；Couchbase 卖的是「一套里同时又快又能当库」，省的是拆两套带来的复杂度和一致性成本，不是魔法功能。

## 问题 5：MongoDB 和 Couchbase 都支持对 JSON 的 KV 读写以及 JSON 字段建索引吗？

**参考答案：** 对，可以这么理解。两者都支持：

1. **按 key / id 做 KV 式读写**  
   - MongoDB：通常用 `_id`（或自定义唯一键）整文档读写，例如 `findOne` / `replaceOne`  
   - Couchbase：用 document id 做 `get` / `upsert`  
   都是「拿着这个 id，整份 JSON 直接读写」。

2. **对 JSON 里的字段建索引**  
   - 例如按 `userId`、`status`、`createdAt` 建索引，再按条件查  
   - 两边都能做（具体语法、索引类型、能力边界不同）

所以：「JSON 文档 + 按 id 读写 + 字段可索引」是文档库的共同能力，不是 Couchbase 独有。差别更多在内存加速有多强、分布式/运维模型、查询生态、以及要不要再配 Redis，而不是「一边能 KV/索引、另一边不能」。

## 问题 6：MongoDB 和 Couchbase 在用法上有什么区别？

**参考答案：** 能力上都是文档库，差别主要在怎么写、怎么查、怎么和缓存配合。

**1. 按 id 读写（KV 味道）**

- MongoDB 更像「数据库 API」：集合 + 查询/替换，例如 `db.users.findOne({ _id: "u123" })`、`replaceOne(..., { upsert: true })`。
- Couchbase 更像「缓存/KV API」：例如 `collection.get("u123")`、`collection.upsert("u123", doc)`。

体感上：Couchbase 的日常热路径经常是 `get(id)` / `upsert(id, doc)`；MongoDB 虽也能按 `_id` 很快取，但写法始终是集合查询风格。

**2. 按字段查 + 建索引**

- MongoDB：查询语言就是主菜，例如 `createIndex({ status: 1, createdAt: -1 })` 再 `find({ status: "active" })`；聚合、嵌套字段、数组查询很常见。
- Couchbase：KV 是一条路，条件查询通常另走 N1QL（长得像 SQL）或 Search。用法常分两档——知道 id 直接 KV `get`；要按字段筛再用 N1QL / 索引服务。MongoDB 则更统一：多数读写走同一套 query API。

**3. 和「快」相关的用法习惯**

| | 常见用法 |
|---|---|
| MongoDB | 业务数据进 Mongo；要极速热数据时另加 Redis，自己管失效 |
| Couchbase | 热路径尽量 `get(id)`，指望工作集在内存；复杂条件再走查询 |

同一业务常见路径：

- Mongo 团队：`读 Redis → miss → 读 Mongo → 回填 Redis`
- Couchbase 团队：很多场景直接 `get(docId)`，少一层自建缓存（重查询仍可能另配缓存）

**一句话：** 数据能力上两边都能「JSON + 按 id 读写 + 字段索引」；用法上 Mongo 更统一地用「集合查询」，Couchbase 更常把「按 id 的 KV」和「像 SQL 的查询」拆成两种访问方式，并更鼓励热路径走 KV。

## 问题 7：文档提到 Redis 不支持 multi-DC，这是为什么？

**参考答案：** 选型树里的「不支持 multi-DC」，更准确是指：**开源 Redis / Redis Cluster 没有一等公民的跨机房多活能力**，不是「绝对不能跨机房放机器」。爱奇艺原分享大意是：Redis Cluster 功能受限，例如不支持明确的跨 DC 部署和访问，读写主要在主库；跨集群同步要自己做。

主要原因：

1. **设计假设是同机房、低延迟**  
   Redis Cluster 的心跳、故障检测、槽位迁移按毫秒级内网设计。机房间 RTT 往往几十毫秒，容易误判超时、频繁 failover，复制积压也更重。爱奇艺也提到 Redis 对网络抖动非常敏感。

2. **没有 Couchbase 那种集群间复制产品能力**  
   Couchbase 有 XDCR（跨数据中心复制）：集群独立，可单向/双向同步。开源 Redis Cluster 只管一个集群内部，不提供集群 A ↔ 集群 B 的官方同步。要多 IDC，只能自研（如 Proxy + Kafka 旁路同步），还常没有冲突检测，业务得做单元化。

3. **天然偏单主写入**  
   一个 key 的写只打主节点。跨机房若两边都能写同一批 key，开源版没有原生冲突解决（商业版 Redis Active-Active / CRDT 才补这块）。选型树语境里的 multi-DC，多半指多活 / 异地可切换读写，不是「从库放远一点」。

对比：

| | Redis Cluster（开源） | Couchbase |
|---|---|---|
| 集群内分片 | 有 | 有（vBucket） |
| 跨机房官方复制 | 基本没有 | XDCR 有 |
| 跨 DC 多活 | 弱，常需自研 | 产品能力更强 |
| 网络敏感度 | 很高 | 相对更适合跨集群同步场景 |

怎么理解图上那句「不支持」：不是物理禁止跨机房，而是原生不好用 / 官方不推荐把一个 Cluster 跨 DC，也没有好用的多集群多活方案；要做就得自研，还一堆限制。所以选型树里：要 multi-DC 的 KV/文档场景，倾向 Couchbase（或后来的 HiKV）；Redis 更适合单 DC / 本机房内的缓存与高速 KV。补充：若用 Redis Enterprise Active-Active 等商业能力，故事会不一样；爱奇艺那张树说的是当时开源 Redis 的实践结论。
