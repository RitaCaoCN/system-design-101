# [HTTP/1 -> HTTP/2 -> HTTP/3](../translations/zh/http1-http2-http3.zh.md)

阅读时间：2026-06-02

## 问题 1：HTTP/2 “解决了 HTTP 层的队头阻塞，但没有解决 TCP 层的队头阻塞”是什么意思？

**参考答案：** 队头阻塞可以理解为：排在前面的任务卡住了，导致后面的任务即使已经准备好，也不能继续往前走。

在 HTTP/1.1 中，如果多个请求复用同一个 TCP 连接，请求和响应通常需要按顺序处理。例如：

```text
请求 A：/big-report，很慢
请求 B：/style.css，很快
请求 C：/logo.png，很快
```

如果 A、B、C 在同一个 HTTP/1.1 连接上，B 和 C 即使处理得很快，也可能要等 A 返回之后才能返回。这种阻塞发生在 HTTP 请求/响应的调度层面，所以叫 HTTP 层的队头阻塞。

HTTP/2 引入了多路复用。它可以在同一个 TCP 连接里同时承载多个 stream：

```text
TCP connection
  stream A: /big-report
  stream B: /style.css
  stream C: /logo.png
```

这样，B 和 C 的响应数据可以和 A 的响应数据穿插着返回，不必等 A 完整结束。因此，HTTP/2 解决了 HTTP 层的队头阻塞，也减少了浏览器为了并发加载资源而打开多个 TCP 连接的需求。

但是 HTTP/2 仍然运行在 TCP 之上，而 TCP 有一个重要特性：它向上层应用提供的是可靠、有序的字节流。也就是说，TCP 必须按照顺序把数据交给上层。

假设底层 TCP 包的到达情况是：

```text
packet 1：到达
packet 2：丢失
packet 3：到达
packet 4：到达
packet 5：到达
```

即使 packet 3、4、5 已经到达，TCP 也不能先把它们交给 HTTP/2，因为 packet 2 丢了。TCP 必须等 packet 2 重传成功后，才能继续按顺序交付后面的数据。

这就是 TCP 层的队头阻塞。阻塞不是因为某个 HTTP 请求太慢，而是因为底层 TCP 字节流中间缺了一段数据，导致整个 TCP 连接上的后续数据都被卡住。由于 HTTP/2 的多个 stream 共用同一个 TCP 连接，一个 TCP 包丢失可能会影响这个连接上的所有 stream。

HTTP/3 使用 QUIC 来改善这个问题。QUIC 同样支持多路复用，但它在传输层把不同 stream 管理得更独立。一个 stream 发生丢包时，通常不会阻塞其他 stream 的数据继续交付：

```text
QUIC connection
  stream A：丢包，等待重传
  stream B：继续传输
  stream C：继续传输
```

所以可以总结为：

```text
HTTP/1.1：容易出现 HTTP 层队头阻塞
HTTP/2：解决 HTTP 层队头阻塞，但仍可能遇到 TCP 层队头阻塞
HTTP/3：基于 QUIC，进一步减少传输层队头阻塞的影响
```

## 问题 2：TLS 是 Transport Layer Safety 吗？

**参考答案：** 不是。TLS 的全称是 Transport Layer Security，中文通常叫传输层安全协议。

TLS 主要解决三个问题：

1. 加密：防止通信内容被中间人直接读懂。例如用户提交密码、Cookie、Token 时，即使网络被抓包，攻击者也不应该看到明文内容。
2. 身份认证：确认客户端连接到的服务器确实是目标服务器。例如访问 `https://example.com` 时，浏览器会通过证书验证服务器身份，避免用户被伪装网站欺骗。
3. 完整性校验：防止数据在传输过程中被篡改。例如攻击者不能在不被发现的情况下，把服务器返回的页面内容偷偷改掉。

HTTPS 可以理解为 HTTP + TLS。传统的 HTTPS 通常是：

```text
HTTP
TLS
TCP
IP
```

也就是 HTTP 数据先经过 TLS 加密，再通过 TCP 可靠传输。

TLS 和 TCP 的职责不同：

```text
TCP：负责可靠传输、按序交付、丢包重传、拥塞控制
TLS：负责加密、身份认证、完整性保护
HTTP：负责请求/响应语义，例如 GET、POST、Header、Status Code
```

在 HTTP/1.1 和 HTTP/2 中，如果使用 HTTPS，通常都是基于 TLS over TCP。而 HTTP/3 不再使用 TCP，它运行在 QUIC 之上。QUIC 内部集成了 TLS 1.3，所以 HTTP/3 默认就是加密的。

可以简单记：

```text
TLS = Transport Layer Security
不是 Transport Layer Safety
```

## 问题 3：什么是 QUIC？

**参考答案：** QUIC 是一个基于 UDP 的现代传输协议。它最早由 Google 推动，后来被 IETF 标准化。HTTP/3 就是运行在 QUIC 之上的 HTTP 版本。

传统 HTTP/2 的协议栈大致是：

```text
HTTP/2
TLS
TCP
IP
```

HTTP/3 的协议栈大致是：

```text
HTTP/3
QUIC, including TLS 1.3
UDP
IP
```

UDP 本身是不可靠的：它不保证数据一定到达，也不保证顺序，还不负责丢包重传。但 QUIC 并不是直接依赖 UDP 的“不可靠特性”来传 HTTP。更准确地说，QUIC 使用 UDP 作为底座，然后在用户态自己实现了很多原本由 TCP 或 TLS 提供的能力，包括：

```text
可靠传输
丢包重传
拥塞控制
流量控制
多路复用
连接管理
加密传输
```

所以 HTTP/3 并不是“不可靠的 HTTP”。它是通过 QUIC，在 UDP 之上重新实现了一套可靠、安全、支持多路复用的传输机制。

QUIC 选择基于 UDP，一个重要原因是 TCP 很难大幅修改。TCP 的实现通常在操作系统内核中，协议升级和部署周期很长。而 QUIC 大多在用户态实现，浏览器、服务器、客户端库可以更快迭代协议能力。

QUIC 的几个核心优势：

1. 减少队头阻塞影响

HTTP/2 虽然支持多路复用，但多个 stream 仍然共享同一个 TCP 字节流。如果 TCP 层丢包，整个连接的后续数据交付可能被阻塞。QUIC 在传输层原生支持多个 stream，一个 stream 丢包时，其他 stream 通常可以继续向上交付数据。

2. 握手更快

传统 HTTPS 连接通常需要先进行 TCP 握手，再进行 TLS 握手，然后才能发送 HTTP 请求。QUIC 把传输握手和 TLS 1.3 加密握手结合起来，可以减少建立连接所需的往返次数。在访问过的网站上，还可能支持 0-RTT，让客户端更快发送早期数据。

3. 支持连接迁移

TCP 连接通常由源 IP、源端口、目标 IP、目标端口这四个信息标识。如果手机从 Wi-Fi 切换到 4G，IP 地址变化，原来的 TCP 连接往往会断开。

QUIC 使用 Connection ID 来标识连接。即使网络变化，只要连接 ID 还能对应上，QUIC 就有机会保持连接继续可用。这对移动端、弱网、网络切换场景很有价值。

4. 默认集成加密

QUIC 内部集成 TLS 1.3。HTTP/3 实际使用时默认就是加密传输，这也让中间设备更难随意篡改或依赖旧式方式解析传输内容。

5. 更适合现代网络

现代 Web 页面通常包含大量资源，用户也经常处在移动网络、Wi-Fi 切换、弱网和高丢包环境中。QUIC 的多路复用、连接迁移和更快握手，都是为了改善这些场景下的体验。

可以用一个不完全精确但好理解的类比：

```text
TCP 像一条严格按顺序交付的单车道。
前面一段缺了，后面的内容即使到了，也要等它补上。

QUIC 像在一个连接里管理多条相对独立的通道。
某条通道丢了数据，其他通道还能继续前进。
```

总结来说，QUIC 不是简单地“用 UDP 替代 TCP”，而是在 UDP 之上实现了一套更适合 HTTP/3 的现代传输层：可靠、安全、低延迟、支持多路复用，并且更适合移动网络。
