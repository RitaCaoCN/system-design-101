# [API 设计中如何进行分页？](../translations/zh/how-do-we-perform-pagination-in-api-design.zh.md)

阅读时间：2026-06-01

## 问题 1：基于 cursor 的分页是怎么做的？

**参考答案：** 基于 cursor 的分页不是用页码或 offset 表示“第几页”，而是用一个 cursor 表示“从哪条记录之后继续读取”。服务端返回一页数据时，会根据当前页最后一条记录的排序字段生成 `next_cursor`，客户端请求下一页时再把这个 cursor 带回来。

例如订单列表按 `created_at DESC, id DESC` 排序时，cursor 里可以编码最后一条记录的 `created_at` 和 `id`。下一页查询时，服务端解码 cursor，然后使用类似下面的条件继续读取：

```sql
SELECT *
FROM orders
WHERE (created_at, id) < (:created_at, :id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

这样数据库可以利用索引从指定位置继续扫描，不需要像 `offset=100000` 那样跳过大量记录，因此更适合大数据集、信息流、订单列表、消息列表、日志列表等连续加载场景。

## 问题 2：cursor 是存放在数据库表里的吗？

**参考答案：** 普通列表分页里，cursor 通常不需要存进数据库表。它一般是服务端根据当前页最后一条记录临时生成的编码字符串，返回给客户端；客户端下一次请求时原样带回。数据库中真正需要存在的是用于排序和定位的字段，例如 `id`、`created_at`，以及支持这些字段的索引。

少数复杂场景可能会把 cursor 状态存到服务端，例如复杂搜索、导出任务、快照分页、游标有效期控制等。这时 cursor 可能只是一个 token，对应服务端缓存或表中的查询状态。但常规 API 分页中，cursor 更多是由已有排序字段生成的位置凭证。

## 问题 3：是不是因为 `id` 是唯一索引，所以才可以用 cursor 这样分页？

**参考答案：** 是的，`id` 唯一很关键，因为它可以帮助确定一个稳定、无歧义的位置。更准确地说，cursor 分页通常依赖一组稳定排序键，而不是只依赖单个字段。

例如使用：

```sql
ORDER BY created_at DESC, id DESC
```

这里 `created_at` 可能重复，所以还需要唯一的 `id` 作为兜底排序字段。如果只按 `created_at` 分页，当多条记录拥有相同时间戳时，下一页查询可能跳过还没返回的数据，或者返回重复数据。

因此，用于 cursor 的排序条件通常需要满足：

1. 排序稳定；
2. 能唯一确定一条记录的位置；
3. 最好有索引支持，例如 `(created_at, id)`。
