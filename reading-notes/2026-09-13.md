# [如何实现读副本模式](/Users/rita/study/system-design-101/translations/zh/how-to-implement-read-replica-pattern.zh.md)

阅读时间：2026-09-13

## 问题 1：这篇有没有读写分离的中间件介绍？

**参考答案：** 有。整篇就是在讲用**数据库中间件**做读副本（读写分离），而不是应用内路由。要点：

1. 两种实现：应用内路由 vs 数据库中间件（本文重点是后者）。
2. 中间件在应用和数据库之间做透明路由，可按用户、schema、语句等规则分流；写走主库，读走副本。
3. 用标准 MySQL 网络协议做代理，兼容 MySQL 客户端。
4. 优点：简化应用、兼容性好；缺点：增加复杂度与延迟，需要高可用，避免单点。

注意：文中是**概念级介绍**，没有点名具体产品（如 ProxySQL、MaxScale 等）。同主题还有英文篇 `data/guides/database-middleware.md`，内容基本一致。

## 问题 2：有哪些常见的读写分离相关中间件？

**参考答案：** 仓库本身没有产品级介绍；常见选型如下。

**MySQL 生态（最贴近原文）：**

| 中间件 | 定位 | 读写分离能力 |
|--------|------|----------------|
| ProxySQL | 开源 MySQL 代理，生产常用 | 按 SQL 规则把读/写分到不同 hostgroup；连接池、查询缓存、故障切换 |
| MaxScale（MariaDB） | 官方代理 | `readwritesplit` 路由；还可做 binlog、防火墙等 |
| MySQL Router | MySQL 官方路由 | 配合 InnoDB Cluster；读写分离相对轻量 |
| ShardingSphere-Proxy | 分库分表 + 代理 | 读写分离是基础能力，还能分片、加密等 |
| Vitess | 面向超大规模 | 分片为主，顺带路由；偏整站级方案 |

国内曾常见 Atlas、OneProxy、MyCat，多已老化或停更，新项目一般不优先选。

**PostgreSQL：** PgBouncer 主要是连接池，本身不做智能读写分离；Pgpool-II 更接近「连接池 + 读写分离」中间件。

**选型直觉：** 只要 MySQL 读写分离、少改应用 → ProxySQL / MaxScale；还要分库分表 → ShardingSphere / Vitess；Postgres 先解决连接数 → PgBouncer，要代理层分流 → Pgpool-II；云上也可用托管能力（RDS Proxy、Aurora Reader endpoint 等）。

# [IBM MQ -> RabbitMQ -> Kafka -> Pulsar：消息队列演进](/Users/rita/study/system-design-101/translations/zh/how-do-message-queue-architectures-evolve.zh.md)

阅读时间：2026-09-13

## 问题 1：RabbitMQ 里 exchange type 的 direct、topic、fanout 是干什么用的？

**参考答案：** 文中只点名未展开。三者都是 **Exchange 把消息路由到 Queue 的规则**；生产者发到 Exchange，不直接发队列。

- **routing key**：发消息时带的标签；**binding key**：队列绑到 Exchange 时的匹配规则。
- **direct**：routing key 与 binding key **完全相等**才进队；适合精确分流。
- **topic**：通配符匹配（`*` 一段、`#` 多段）；适合按主题层次订阅。
- **fanout**：**忽略** routing key，绑到该 Exchange 的队列各收一份；适合广播。

另有较少提的 **headers** 类型（按消息头匹配）；原文未写。

## 问题 2：Exchange 是什么？

**参考答案：** Exchange 是 RabbitMQ 里的**路由枢纽**（逻辑对象），不是独立机器。链路是：`生产者 → Exchange →（按 type + binding 路由）→ Queue(s) → 消费者`。队列像邮箱，Exchange 像邮局分拣台；作用是把生产与「谁消费、有几个队列」解耦。direct/topic/fanout 是 Exchange 的分拣策略，不是三种队列。

## 问题 3：Exchange 是单点吗？多个 Exchange 如何同步路由策略？「集群把配置复制到三台」是什么意思？

**参考答案：**

- Exchange 是 broker 内的**逻辑配置**（名字 + 类型 + binding），不是单独一台「Exchange 服务器」。
- **单机**：整台 broker（含 Exchange）是单点。
- **集群**：逻辑上仍是**一个** Exchange；你在任一节点 declare/bind 后，配置作为**集群元数据**复制到各节点，每台都有同一份路由表，消息打到哪台就在哪台按本地副本路由——**不是**多个同名 Exchange 各自为政再互相同步。
- **多个独立集群**：默认不同步；要靠两边各自配置，或用 Federation / Shovel 传消息。

「复制到三台」复制的是**配置**（有哪些 Exchange、类型、谁绑了谁），不是消息内容。像多个窗口柜员人手一份相同的分拣规则复印件。

## 问题 4：RabbitMQ 用的分布式存储是什么？为什么不用 MySQL/Redis？队列数据存在哪？

**参考答案：** 要分开看 **元数据** 和 **消息**。

**元数据**（Exchange、binding、队列定义等）：

| 存储 | 说明 |
|------|------|
| **Mnesia** | Erlang 自带；长期默认，至 3.13 基本唯一 |
| **Khepri** | 基于 Raft；4.0 正式支持；**4.2 起新部署默认**；老集群升级后仍用 Mnesia 直到显式切换 |

不用默认外挂 MySQL/Redis，因为元数据是 broker「神经系统」：要低延迟、与集群成员强绑定、故障域小；外置库会多一跳依赖，还得自己处理缓存与脑裂。MySQL/Redis 更适合业务侧外围，不适合替换内置路由表。

**消息内容**（不在 Mnesia/Khepri）：

| 队列类型 | 消息存在哪 |
|----------|------------|
| Classic | 节点本地内存 + 磁盘消息存储 |
| Quorum | 多节点 Raft 日志（现代高可用首选） |
| Stream | 追加日志，可多副本，适合回放 |

落盘在 RabbitMQ 节点 data 目录，不是业务 MySQL。配置是否三机一份 ≠ 消息是否三份——后者取决于队列类型（经典 / quorum / stream 等）。

## 问题 5：RabbitMQ 不用考虑高可用也可以用吗？看起来没有 partition 的概念

**参考答案：** **可以。** 单机 RabbitMQ 很常见；它也确实**没有 Kafka 那种 partition**。但这不等于生产完全不用想高可用和扩展。

| | RabbitMQ | Kafka |
|--|----------|--------|
| 核心抽象 | Exchange → Queue | Topic → **Partition** |
| 并行消费 | 多消费者抢同一队列，或拆多队列 | 靠**多 partition** 并行；partition 内有序 |
| 扩展方式 | 加队列/节点、quorum/stream；复杂时应用层分片 | 加 partition / broker |

**可以先不搞集群：** 学习开发、流量小、可接受短暂停服或丢少量非关键消息 → 单机 + 经典队列即可。

**生产仍常要考虑：** 单机故障 → 集群 + **quorum queue**；消费跟不上 → 多消费者 / 多队列 / Stream；要严格按 key 分区有序 + 海量吞吐 → 更常选 Kafka（RabbitMQ 也能用多队列「人工分区」，但非长项）。

一句话：没 partition ≠ 不能用，也 ≠ 不用考虑 HA；只是扩展模型不同。路由/任务队列偏 RabbitMQ；事件流、replay、按 key 分区并行偏 Kafka/Pulsar。

# [CAP 定理：最容易被误解的术语之一](/Users/rita/study/system-design-101/translations/zh/cap-theorem-one-of-the-most-misunderstood-terms.zh.md)

阅读时间：2026-09-13

## 问题 1：partition tolerance 是什么？和 availability 有什么关系？

**参考答案：**

- **Partition Tolerance（P）**：出现网络分区（节点间通信断开、形成多个「岛」）时，系统仍能作为分布式系统继续运行。
- **Availability（A）**：客户端请求仍能得到响应（即使部分节点有问题）。

两者相关但不是一回事：P 问的是「切开了还承不承认继续跑」；A 问的是「客户端还能不能拿到应答」。CAP 关键点在于：**一旦真的分区，完美的 C 和完美的 A 不能同时保住**——保 C 往往要让少数派拒绝写入（损 A）；保 A 则两边都可能继续写（损 C）。真实网络里 P 几乎必选，实践常在 **CP vs AP** 里选。文中也提醒：分区相对少见，更日常的是无分区时的延迟 vs 一致性（PACELC）。

## 问题 2：没有 P 会怎么样？

**参考答案：** 没有 P ≈ 网络一切开，系统**不承诺**还能安全地当分布式系统跑下去。常见表现：

1. 探测到分区就停服 / 退化单机；
2. 设计假设「节点永远能互通」，真断网时脑裂、双主或行为未定义；
3. 单机系统本身没有节点间分区问题，CAP 的 P 基本不适用。

有 P 则是：切开了也继续按策略跑，但必须在 C 与 A 之间取舍。所以多机部署通常承认 P，再选分区期间保 C 还是保 A。

# [数据库类型](/Users/rita/study/system-design-101/translations/zh/types-of-databases.zh.md)

阅读时间：2026-09-13

## 问题 1：OLAP 数据库和 hierarchical DB 有什么关系？

**参考答案：** 正文未提 Hierarchical DB。图鉴里若二者并排，通常是**并列类型**，不是包含关系。

- **Hierarchical DB**：树形数据模型（父子记录），如老式 IMS、部分目录思路。
- **OLAP DB**：按用途分类——为报表/分析优化。

分类轴不同（模型 vs 负载）。容易混的是：OLAP 维度常有 hierarchy（年→季→月，方便上卷下钻），那是**分析维度层级**，不等于 Hierarchical DB 这种库。

## 问题 2：Doris 是不是也属于 OLAP？

**参考答案：** **是。** Apache Doris 一般归为实时/分析型 OLAP（MPP 列式），面向报表、多维分析、明细查询，不宜当高并发事务主库。同类常见还有 ClickHouse、Druid、StarRocks 等。

## 问题 3：OLAP 和关系型数据库的主要区别就是「业务实时落盘 vs 离线分析」吗？

**参考答案：** **不完全是。** 更准确的对照是 **OLTP vs OLAP**，不是「关系型 vs OLAP」。

- **关系型**是数据模型；**OLAP/OLTP**是用途/负载。很多 OLAP 也用 SQL/表（Doris、Snowflake 等）。
- **OLTP**：短事务、少量行、高并发读写，优化行存/索引/事务。
- **OLAP**：大范围扫描与聚合，优化列存/压缩/并行等。
- 「OLAP = 离线」不准确：Online 指交互式分析查询；Doris 等常支持近实时导入。关系型也能做分析，大数据量重聚合时往往不如专用 OLAP。

常见架构：关系型 OLTP 扛业务 → 同步到 OLAP 做分析（可离线，也可近实时）。

## 问题 4：四种 NoSQL 数据库可以分别举例吗？

**参考答案：**

| 类型 | 是什么 | 常见例子 |
|------|--------|----------|
| 图（Graph） | 节点+边存关系 | Neo4j、Amazon Neptune、JanusGraph |
| 键值（Key-value） | key → value | Redis、DynamoDB、Riak、etcd |
| 文档（Document） | JSON/BSON 类文档 | MongoDB、CouchDB、DocumentDB、FirestoreDB（文档接口） |
| 列式/宽列（Column） | 按列或列族组织 | Cassandra、HBase、Scylladb；分析向列存还有 ClickHouse（也常归 OLAP） |

分类会有重叠（如 Redis、DynamoDB），入门按上表记即可。

## 问题 5：MongoDB 和 CouchDB 是不是也支持 SQL？

**参考答案：** **原生都不是 SQL 数据库**；「支持 SQL」多半指额外接口，不是像 Postgres 那样以 SQL 为一等公民。

- **MongoDB**：主接口是 MQL；Atlas SQL、BI Connector 等可把 SQL 转成 Mongo 查询，方便 BI。能用 SQL 查 ≠ 变成关系型库。
- **CouchDB**：主接口是 HTTP/JSON、Mango Query、MapReduce；一般没有完整内置标准 SQL 引擎。

NoSQL 常作 Not Only SQL：底下可以是文档模型，上面再挂 SQL 方言。选型仍看文档 API 与事务/连接能力，别和真正的 SQL 库划等号。

## 问题 6：图上的 Object Relational Mapping（ORM）是什么意思？

**参考答案：** ORM = **对象关系映射（Object-Relational Mapping）**：一套框架，把高级语言里的**对象**翻译成关系库里的**表/行**，也把查询结果翻译回对象。它**不是一种数据库**，而是应用代码和关系型数据库之间的访问层。

两边「说话方式」不同：

- 程序里：`User` 对象，有 `name`、`email`
- 库里：`users` 表，有 `name`、`email` 列

**没有 ORM：** 自己写 SQL，再把结果一行行塞进对象（`SELECT` 后手动 `new User`；改名字自己拼 `UPDATE`）。  
**有 ORM：** 主要跟对象打交道，框架生成 SQL 并填回对象，例如：

```text
user.name = "Alice"  →  ORM  →  UPDATE users SET name='Alice' WHERE id=1
User.find(1)       ←  ORM  ←  SELECT * FROM users WHERE id=1
```

类比：你只会中文点菜，餐厅只认菜单编号；ORM 像服务员，帮你把「宫保鸡丁」对成「48 号」。常见框架：Hibernate、SQLAlchemy、Prisma、Django ORM、ActiveRecord、TypeORM 等。

## 问题 7：所以 NoSQL 就是 ORM 起作用了？

**参考答案：** **不是。** NoSQL 和 ORM 是两件不同的事，没有「NoSQL = ORM 起作用」这种关系。

| | 是什么 |
|--|--|
| 关系型数据库 | 用表存数据（MySQL、Postgres） |
| ORM | 写代码时的翻译工具：对象 ↔ 关系表；主要配关系型库 |
| NoSQL | 另一类数据库（文档 / KV / 图 / 列等），模型本来就不是（或不主要是）表 |

```text
应用代码
   ├─ 用 ORM ──────────► 关系型数据库（表）
   └─ 用官方 SDK/驱动 ─► NoSQL（文档、KV…）
```

有 ORM ≠ 变成 NoSQL；用 NoSQL ≠ 一定用 ORM。MongoDB 等常直接操作文档，往往不需要「对象→表」的 ORM；若有对象↔文档映射，有时叫 **ODM**，也不是关系型 ORM 的定义。

## 问题 8：ORM 是针对关系型数据库的吗？「翻译官」是 SDK 吗？

**参考答案：** **对，ORM 主要针对关系型数据库**（对象 ↔ 表）。「翻译官」指的是 **ORM 框架本身**，**不完全等于 SDK**。

可以叠两层看：

```text
业务代码
    ↓
ORM 框架          ← 「对象 ↔ 表/SQL」的翻译官（Hibernate、SQLAlchemy、Prisma）
    ↓
数据库驱动/客户端  ← 常被叫 SDK、driver、client：连库、发协议、收结果
    ↓
MySQL / Postgres …
```

| 层级 | 干什么 | 例子 |
|------|--------|------|
| 驱动 / SDK | 连上库、执行你给的 SQL/命令 | JDBC 驱动、`psycopg`、`mysql-connector` |
| ORM | 把对象操作变成 SQL，再把结果填回对象；底下通常调用驱动 | Hibernate、SQLAlchemy、Prisma |

驱动/SDK 像电话线；ORM 像翻译官。没有 ORM 也可以只用 SDK 自己写 SQL。NoSQL 也有各自的 SDK/驱动，那是「怎么连、怎么发命令」，一般不叫 ORM。

## 问题 9：Hibernate、SQLAlchemy、Prisma 怎么用？可以举例吗？

**参考答案：** 三者角色相同：先定义「对象/模型长什么样」，再增删改查；框架去生成 SQL。差别主要在语言和 API 风格。下面用同一件事——存/查一个用户——对照。

**Prisma（TypeScript / Node）** — 先在 schema 定义模型：

```prisma
model User {
  id    Int    @id @default(autoincrement())
  name  String
  email String @unique
}
```

```ts
await prisma.user.create({
  data: { name: "Alice", email: "a@example.com" },
});
const user = await prisma.user.findUnique({
  where: { email: "a@example.com" },
});
```

**SQLAlchemy（Python）：**

```python
class User(Base):
    __tablename__ = "users"
    id = Column(Integer, primary_key=True)
    name = Column(String)
    email = Column(String, unique=True)

user = User(name="Alice", email="a@example.com")
session.add(user)
session.commit()

user = session.query(User).filter_by(email="a@example.com").one()
# 较新写法也常用 select / session.scalars(...)
```

**Hibernate（Java）：**

```java
@Entity
@Table(name = "users")
public class User {
    @Id @GeneratedValue
    private Long id;
    private String name;
    private String email;
}

User user = new User();
user.setName("Alice");
user.setEmail("a@example.com");
session.persist(user);
session.getTransaction().commit();

User u = session.createQuery(
    "from User u where u.email = :email", User.class)
    .setParameter("email", "a@example.com")
    .getSingleResult();
```

| | 你写什么 | 框架干什么 |
|--|----------|------------|
| 无 ORM | `INSERT INTO users ...` / `SELECT ...` | 无，自己管 SQL |
| 有 ORM | `create` / `add` / `persist` 一个 User | 生成 SQL，读写表，填回对象 |

实际项目里还要配数据库连接、跑迁移建表等；核心就是「定义模型 → 对象操作 → 自动 SQL」。

# [数据库锁解释](/Users/rita/study/system-design-101/translations/zh/what-are-the-differences-among-database-locks.zh.md)

阅读时间：2026-09-13

## 问题 1：为什么有一个更新锁？

**参考答案：** 文中说更新锁（U Lock）用于防止事务打算更新某资源时出现死锁。它是给「先读后改」准备的**中间锁**，避免两个事务都先拿共享锁再抢着升排他锁时卡死。

**没有 U 时的死锁（经典）：**

```text
事务 A、B 都先拿 S 读同一行（S 与 S 兼容）
双方都要改 → 都想把 S 升级成 X
A 等 B 放 S，B 等 A 放 S → 死锁
```

**有 U 时：** 打算更新时先拿 U，真正写入再升 X。同一资源上通常只允许一个 U，另一个要等；不会出现「两个都握着 S、同时升 X」。

为何不直接上 X：一上来 X 并发差；只用 S 能并发读但易升级死锁。U 介于两者之间：读阶段相对友好，但「谁有权稍后去改」是独占的。

注意：独立 U 锁在 SQL Server 里很典型；MySQL/InnoDB 等机制不同，但「避免锁升级死锁」这类问题共通。

## 问题 2：行级锁和页级锁有什么用？

**参考答案：** 两者都是锁的**粒度**（锁住多大一块数据），用来在并发时保护一致性；差别主要是并发度 vs 开销。和 S/X/U（锁**模式**）是不同维度：模式决定允不允许别人读/写，粒度决定覆盖范围。

| | 行级锁 | 页级锁 | （对照）表级锁 |
|--|--------|--------|----------------|
| 锁什么 | 某一行 | 一页（固定大小块，内含多行） | 整张表 |
| 用处 | 改一行时其他行仍可访问 → **并发高** | 一次锁多行，锁数量少 → **管理开销小** | 实现最简单 |
| 代价 | 锁多、管理成本高，可能锁升级 | 只改一行也可能挡住同页其他行（假冲突） | 并发最差 |

文中：行级锁锁定某一行并允许其他行并发；页级锁锁定一页数据块。现代 OLTP（如 InnoDB）以行锁为主，页/表锁更多是补充或升级结果。

## 问题 1：Flink 是什么？

**参考答案：** 正文未写 Flink，配图里常和 Kafka 画在一起。**Apache Flink** 是分布式**流式计算引擎**：从 Kafka 等持续读数据，做实时计算（过滤、聚合、窗口等），再写出到库、回 Kafka 或触发告警。

| | 角色 |
|--|------|
| Kafka | 消息/事件的管道与存储（可重放） |
| Flink | 在流上算（有状态、低延迟） |

常见链路：`业务/CDC → Kafka → Flink → 结果表 / 告警 / 另一 topic`。一句话：Kafka 负责流过去，Flink 负责实时算。

## 问题 2：为什么日志分析很适合用 Kafka + ES + Kibana？

**参考答案：** 三者各管一段，覆盖「海量日志从产生到可搜可看」。

| 组件 | 角色 | 为何适合日志 |
|------|------|----------------|
| Kafka | 缓冲 + 解耦管道 | 削峰；生产只快写；多消费者；可重放 |
| Elasticsearch | 可搜索存储 | 全文检索、按字段/时间过滤与聚合 |
| Kibana | 查询与可视化 | 检索、仪表盘，少写代码 |

链路：`采集 → Kafka → 写入 ES → Kibana`。适合点：突发削峰、产消解耦、一份日志多用途、检索形态匹配、规则变更可重放重建索引。

## 问题 3：为什么也适合做 Change Data Capture（CDC）？

**参考答案：** CDC 要把库表变更变成**持续事件流**并可靠扇出给下游；Kafka 适合当变更事件总线（Kafka 不是 CDC 工具本身，常配合 Debezium 等读 binlog/WAL）。

| 需求 | Kafka 怎么对上 |
|------|----------------|
| 变更不停 | 追加型事件流 |
| 库与下游速度差 | 先入 Kafka 削峰 |
| 多下游要同一份变更 | 一 topic 多消费组 |
| 下游故障/逻辑变更 | 保留期内按 offset 重放 |
| 同主键有序 | 按 key 进同一 partition |
| 与业务解耦 | 业务只写 DB，连接器写 Kafka |

和日志分析同类合适：都是高吞吐、追加、解耦、可重放的事件流；内容分别是 app 日志 vs 行变更。
