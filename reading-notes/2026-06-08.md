# [REST API 与 GraphQL](../translations/zh/rest-api-vs-graphql.zh.md)

阅读时间：2026-06-08

## 问题 1：GraphQL 是什么？

**参考答案：** GraphQL 是一种用于 API 的查询语言，也包含一套服务端执行规范。客户端可以声明自己需要哪些数据和字段，服务端按照这个查询返回对应结果。它通常用于前端向 API 服务器查询数据，和 SQL 查询数据库有些相似，但面向的是 API 层的数据。

**Case：** 用户详情页需要展示用户姓名、邮箱和最近文章标题。使用 GraphQL 时，客户端可以一次性声明：

```graphql
{
  user(id: 1) {
    name
    email
    posts {
      title
    }
  }
}
```

服务端只返回这些字段，而不是把用户对象、文章对象里的所有字段都返回。

## 问题 2：GraphQL 是 JSON 请求吗？

**参考答案：** GraphQL 本身不是 JSON，而是一种查询语言。实际通过 HTTP 发送时，常见做法是把 GraphQL 查询字符串放在 JSON 请求体的 `query` 字段里，服务端返回结果通常也是 JSON。因此可以理解为：GraphQL 常用 JSON 作为传输格式，但 GraphQL 本身不是 JSON。

**Case：** 一次 GraphQL HTTP 请求可能长这样：

```json
{
  "query": "{ user(id: 1) { name email } }"
}
```

其中外层是 JSON，`query` 字段里的字符串才是 GraphQL 查询语句。服务端返回：

```json
{
  "data": {
    "user": {
      "name": "Alice",
      "email": "alice@example.com"
    }
  }
}
```

## 问题 3：GraphQL 在业内使用多吗？

**参考答案：** GraphQL 在业内使用不少，属于成熟但偏场景化的 API 技术。REST 仍然更普遍，因为它简单、生态成熟、缓存和调试更直接。GraphQL 更适合复杂前端、多端应用、需要聚合多个数据源、前端需求变化快的场景；但它也会带来服务端实现、权限控制、查询防滥用和缓存方面的复杂度。

**Case：** 一个电商商品详情页可能需要商品信息、库存、价格、评价、推荐商品等数据。如果用 REST，可能需要请求 `/products/1`、`/products/1/inventory`、`/products/1/reviews`、`/products/1/recommendations` 等多个接口；如果用 GraphQL，可以在一次查询里声明这些字段，由 GraphQL 层聚合后返回。

## 问题 4：GraphQL 这个名字的由来是什么？

**参考答案：** GraphQL 可以拆成 Graph + QL。Graph 指数据之间像“图”一样有关联，例如 User、Post、Comment 等对象之间互相连接；QL 是 Query Language，即查询语言。因此 GraphQL 可以理解为“面向图状数据关系的查询语言”：客户端沿着对象关系图声明自己要取哪一部分数据。

**Case：** 数据关系可以看成：

```text
User -> Posts -> Comments
Post -> Author
User -> Followers
```

GraphQL 查询时不是只请求某一个固定 URL，而是沿着这些对象关系选择需要的数据。例如从 `User` 出发，继续取他的 `posts`，再取每篇文章的 `comments`。

## 问题 5：GraphQL 是个中间件吗？

**参考答案：** GraphQL 本身不是中间件，而是一种 API 查询语言和执行规范。它定义客户端如何描述查询、服务端如何理解查询并返回数据。但在实际项目中，GraphQL Server 经常被部署成前端和多个后端服务之间的数据聚合层，因此看起来像一个“中间层”。

**Case：** 一个前端页面需要用户、订单、库存和评价数据时，系统结构可能是：

```text
Frontend
   |
   v
GraphQL API Layer
   |
   +--> User Service
   +--> Order Service
   +--> Inventory Service
   +--> Review Service
```

这时 GraphQL API Layer 接收前端查询，再调用多个后端服务，把结果组装后返回。准确说，GraphQL 不是中间件；但 GraphQL 服务可以作为 API 聚合层或网关层使用。

# [反向代理、API 网关与负载均衡器](../translations/zh/reverse-proxy-vs-api-gateway-vs-load-balancer.zh.md)

阅读时间：2026-06-08

## 问题 1：反向代理和代理有什么区别？

**参考答案：** 单独说“代理”时，通常指正向代理；反向代理是另一种代理模式。两者的核心区别是代理谁、隐藏谁。正向代理代理客户端，目标服务器通常不知道真实客户端是谁；反向代理代理服务器，客户端通常不知道后面真实服务器是谁。

**Case：** 正向代理的请求路径是：

```text
Client -> Forward Proxy -> Server
```

例如公司内网代理帮员工访问外部网站。外部网站看到的是代理服务器的 IP，不一定看到员工电脑的真实地址。

反向代理的请求路径是：

```text
Client -> Reverse Proxy -> Backend Server
```

例如用户访问 `https://example.com`，但真正处理请求的可能是后面的 `10.0.1.12:8080`、`10.0.1.13:8080` 等多台后端机器。用户只知道 `example.com`，不知道真实后端服务器。

**记忆方式：** 正向代理是“客户端的代理”，隐藏客户端；反向代理是“服务器的代理”，隐藏服务器。文档里说反向代理“隐藏真实服务器”，指的就是它站在服务器前面对外接收请求。

# [API 安全的 12 个建议](../translations/zh/top-12-tips-for-api-security.zh.md)

阅读时间：2026-06-08

## 问题 1：这里的“使用 OAuth2”是什么意思？

**参考答案：** 在 API 安全里，“使用 OAuth2”指不要让客户端直接拿用户账号密码访问接口，而是通过 OAuth 2.0 授权机制给客户端发 access token，客户端再带着这个 token 调 API。API 服务会校验 token 是否有效、是否过期、是否有对应权限范围，再决定是否允许访问。

**OAuth2 基本流程：**

```text
1. 客户端把用户跳转到授权服务器
2. 用户在授权服务器登录，并同意授权
3. 授权服务器给客户端一个 authorization code
4. 客户端用 authorization code 向授权服务器换 access token
5. 客户端带着 access token 调用 API
6. API 校验 access token，通过后返回资源
```

**Case：** 第三方代码分析工具想读取用户的 GitHub 仓库。安全做法不是让用户把 GitHub 密码交给工具，而是跳转到 GitHub 授权页面；用户同意“允许读取仓库”后，GitHub 先返回 authorization code；工具的后端再用这个 code 换取 access token；之后工具用这个 token 调 GitHub API。用户以后也可以撤销这个授权。

## 问题 2：既然有 OAuth2，那么有 OAuth1 吗？

**参考答案：** 有 OAuth 1.0，也有修正过安全问题的 OAuth 1.0a。OAuth 1.0/1.0a 是较早的授权协议版本，曾经被一些平台使用，例如早期 Twitter API。现在业内主流是 OAuth 2.0，因为它更适合现代 Web、移动端、前后端分离和开放平台场景，生态也更完整。

**Case：** OAuth 1.0a 更像是每次请求都要带复杂签名，证明“这是我发的，内容没有被改过”；OAuth 2.0 更常见的是先拿到 access token，之后请求时带上：

```http
Authorization: Bearer <access_token>
```

## 问题 3：OAuth 1.0 的逻辑是什么？

**参考答案：** OAuth 1.0 的核心逻辑是：不用把用户密码交给第三方应用，而是通过“临时凭证 + 用户授权 + 请求签名”让第三方访问资源。第三方应用先向平台申请 request token；用户跳转到平台页面同意授权；第三方再把授权后的 request token 换成 access token；之后每次调 API 都用 access token 和 secret 生成签名，API 服务器校验签名后才返回数据。

**Case：** 照片打印网站想读取用户相册。它先向相册平台申请 request token；用户跳到相册平台确认授权；照片打印网站用授权后的 request token 换 access token；之后照片打印网站调用相册 API 时，每个请求都带签名。平台校验签名，确认请求来自持有 secret 的应用，且请求参数没有被篡改。

**记忆方式：** OAuth 1.0 = 授权流程 + 每个 API 请求都要签名。OAuth 2.0 = 授权后拿 access token，之后请求直接带 Bearer token，主要依赖 HTTPS 保护传输。

# [如何设计安全的 Web API 访问](../translations/zh/how-to-design-secure-web-api-access-for-your-website.zh.md)

阅读时间：2026-06-08

## 问题 1：基于 token 的方式，工程上一般如何判断 token 是否过期？

**参考答案：** 工程上判断 token 是否过期，核心是看 token 的过期时间，并且这个判断应该由服务端完成，不能相信客户端自己的时间。

如果使用的是 JWT，token 本身通常会携带一个 `exp` 字段，表示过期时间。`exp` 一般是 Unix 时间戳。服务端收到请求后，会先校验 JWT 签名，确认 token 没有被篡改；然后读取 payload 里的 `exp`，用服务器当前时间和它比较。如果服务器当前时间已经大于或等于 `exp`，就认为 token 过期，通常返回 `401 Unauthorized`，让客户端重新登录或使用 refresh token 换取新的 access token。

如果使用的是 opaque token，也就是 token 本身只是一个随机字符串，服务端不能直接从 token 中读出过期时间。这时服务端通常会去数据库、Redis 或认证服务中查询这个 token 对应的记录。记录里一般会保存 `user_id`、`expires_at`、权限范围等信息。服务端查到记录后，再比较 `expires_at` 和服务器当前时间。如果查不到记录，或者记录已经过期，就拒绝请求。Redis 场景下也可以直接给 token 设置 TTL，过期后 Redis 自动删除，服务端查不到就认为 token 已失效。

实际系统里常见做法是把 token 分成 access token 和 refresh token。access token 生命周期比较短，比如 5 分钟、15 分钟或 1 小时，用来访问 API；refresh token 生命周期比较长，比如 7 天或 30 天，用来在 access token 过期后换取新的 access token。这样即使 access token 泄露，攻击窗口也比较短。

服务端判断过期时通常以自己的时间为准。如果是分布式系统，不同服务器之间可能存在轻微时间差，因此有些系统会允许很小的 clock skew，比如 30 秒到 2 分钟，避免 token 刚签发或刚过期时因为机器时间不同步导致误判。

## 问题 2：文档中的基于 HMAC 的方式是不是一种 JWT？

**参考答案：** 不完全是。文档里的基于 HMAC 的方式更像是“请求签名认证”，不是 JWT 本身。

HMAC 是一种签名/消息认证码算法，JWT 是一种 token 格式。JWT 可以选择用 HMAC 来签名，例如常见的 `HS256` 算法，本质上就是用 HMAC-SHA256 对 JWT 的 header 和 payload 进行签名。此时可以说“这个 JWT 使用了 HMAC 签名”。

但文档中的 HMAC 方案不是把身份信息、过期时间等内容打包成一个 JWT，而是客户端每次发请求时，都根据本次请求的内容生成一个签名。签名通常会基于 HTTP 方法、URL 路径、查询参数、请求体、时间戳、nonce 等字段计算出来。服务端收到请求后，也用同样的字段和同一个 secret 重新计算签名，然后比较客户端传来的签名和服务端算出的签名是否一致。

两者的关注点不同。JWT 更像是“已经签发好的身份证明”，客户端拿着它访问资源，服务端验证 token 是否可信、是否过期、是否有权限。HMAC 请求签名更像是“为每一次请求盖章”，服务端不仅验证调用方是否知道 secret，还能验证请求内容在传输过程中是否被改过。

因此关系可以总结为：HMAC 是一种底层签名算法；JWT 是一种 token 格式；JWT 可以使用 HMAC 签名；但 HMAC 请求签名认证不等于 JWT。文档中的方式更接近 AWS API request signing、Webhook signature、开放平台 API 签名这类机制。

## 问题 3：HMAC 是什么？

**参考答案：** HMAC 全称是 Hash-based Message Authentication Code，中文常叫基于哈希的消息认证码。它的作用是使用一个只有通信双方知道的 secret，对一段消息生成一个认证码，也常被称为签名。这个签名可以用来证明两件事：第一，请求方确实知道 secret，因此大概率是合法调用方；第二，消息内容没有被中途篡改，因为只要消息内容有一点变化，重新计算出来的 HMAC 就会不同。

HMAC 通常写作：

```text
HMAC-SHA256(secret, message)
```

其中 `secret` 是共享密钥，`message` 是要签名的内容，`SHA256` 是使用的哈希函数。真实算法不是简单地把 secret 和 message 拼接后做 hash，而是有标准化的内部结构，用来避免一些普通拼接 hash 可能带来的安全问题。

在 API 请求签名场景中，`message` 往往不是单个字段，而是把请求中的关键内容按约定规则组合起来，例如：

```text
message = HTTP 方法 + URL 路径 + query 参数 + timestamp + nonce + body hash
signature = HMAC-SHA256(api_secret, message)
```

客户端把 `signature` 放到请求 Header 中。服务端收到请求后，根据同样的规则从请求中取出这些字段，使用自己保存的 `api_secret` 再算一遍。如果客户端传来的 signature 和服务端算出来的 signature 一致，说明请求通过认证；如果不一致，说明请求可能被伪造、字段被改过，或者客户端使用了错误的 secret。

HMAC 和普通 hash 的关键区别是有没有 secret。普通 hash 是 `hash(message)`，任何人只要知道 message 就能算出同样的摘要；HMAC 是 `HMAC(secret, message)`，只有知道 secret 的人才能算出正确结果。所以 HMAC 不是为了隐藏消息内容，而是为了认证消息来源和检查消息完整性。

## 问题 4：根据文档中的说法，是客户端持有 APP ID，服务器持有私钥吗？

**参考答案：** 更准确地说，客户端通常持有 `APP ID + API Secret`，服务器保存 `APP ID` 和 `API Secret` 的对应关系。文档里说服务器生成两个 key，一个是公开的 APP ID，另一个是 API Key/私钥。这里的“私钥”容易让人误会成只有服务器持有。实际上，如果客户端需要自己生成 HMAC 签名，那么客户端也必须知道这个 API Secret，否则它没有办法算出正确签名。

一般流程是：服务端为某个调用方分配一个 `app_id` 和一个 `api_secret`。`app_id` 是公开标识，用来告诉服务器“我是谁”；`api_secret` 是共享秘密，只应该被客户端调用方和服务端知道。客户端发请求时，在 Header 或参数里带上 `app_id`、timestamp、nonce、signature 等信息，但不会直接把 `api_secret` 传出去。服务端收到请求后，先根据 `app_id` 查到对应的 `api_secret`，再用这个 secret 和请求内容重新计算签名。

所以这个模型不是非对称加密里的“客户端只有公钥，服务器持有私钥”。它更像共享密钥模型：客户端和服务端都知道同一个 secret，只是请求里传输的是用 secret 算出来的签名，而不是 secret 本身。

这也带来一个重要工程约束：HMAC 请求签名不适合直接放在浏览器前端中使用。因为浏览器里的 JS、网络请求和本地存储都可以被用户查看，如果把 `api_secret` 放进前端代码，就等于把 secret 暴露给所有用户。HMAC 更适合服务端到服务端调用，比如开放平台 API、内部服务调用、Webhook 回调验证等。如果是普通网站前端访问后端 API，通常更适合用登录态 cookie、session、JWT access token 或 OAuth/OIDC 流程。

## 问题 5：HMAC 感觉是不是对称加密？

**参考答案：** HMAC 确实有“对称”的特征，因为客户端和服务端共享同一个 secret。但是严格来说，它不是对称加密，而是基于对称密钥的消息认证机制。

对称加密的目标是保密。发送方用 secret 把明文加密成密文，接收方再用同一个 secret 把密文解密回明文。典型算法是 AES。它解决的问题是：即使别人截获了密文，也看不懂原始内容。

HMAC 的目标不是保密，而是认证和防篡改。发送方用 secret 和 message 生成 signature，接收方用同一个 secret 和收到的 message 再生成一遍 signature，然后比较两个 signature 是否一致。signature 不能被解密回 message，也不隐藏 message 的内容。请求内容本身如果是明文发送，别人仍然可以看到内容；HMAC 只能让别人不能伪造一个合法签名，或者在修改内容后仍然通过校验。

所以可以这样区分：

```text
对称加密：保护内容不被看见，可解密
HMAC：证明内容没被改、请求方知道 secret，不可解密
```

在真实 API 系统里，HMAC 通常还要配合 HTTPS 使用。HTTPS 负责传输过程中的保密和防窃听，HMAC 负责应用层的请求认证、防篡改，有时还会配合 timestamp 和 nonce 防止重放攻击。
